# 步骤 5 子步骤顺序技术方案对比

## 背景

步骤 5（生成 Kuikly 代码）包含 3 个子步骤，其中 5.2 和 5.3 存在两种可选顺序：

- **方案 A（当前）**：5.1 分析 → 5.2 架构定义与骨架生成 → 5.3 逐文件填充
- **方案 B（交换）**：5.1 分析 → 5.2 逐文件完整转换 → 5.3 架构整理与规范化

核心差异在于：**先约束框架再填充业务** vs **先完成业务再统一整理架构**。

## 方案详述

### 方案 A：先骨架后填充（当前方案）

```
5.1 分析文件结构和依赖关系
    ↓ 输出 analysis-report.md + conversion-plan.md
5.2 架构定义与目录搭建
    ↓ 读取 knowledge-cache 中的示例代码
    ↓ 为每个目标文件生成代码骨架（类定义/继承/import/TODO占位）
    ↓ 输出骨架文件到 $OUTPUT_DIR
5.3 逐文件转换
    ↓ 在骨架基础上逐文件填充业务逻辑
    ↓ 输出完整代码文件
```

**工作模式**：骨架作为"模具"约束后续填充，确保所有文件在同一框架下生成。

### 方案 B：先转换后整理（交换方案）

```
5.1 分析文件结构和依赖关系
    ↓ 输出 analysis-report.md + conversion-plan.md
5.2 逐文件完整转换
    ↓ 每个文件独立参照 knowledge-cache 中的示例代码完整转换
    ↓ 输出完整代码文件到 $OUTPUT_DIR
5.3 架构整理与目录规范化
    ↓ 统一审查目录结构、引用关系、架构一致性
    ↓ 修正不符合规范的文件
```

**工作模式**：每个文件独立完整转换，最后统一兜底审查。

## Token 消耗分析

### 方案 A Token 流

| 阶段 | 输入上下文 | 输出 | 工具调用 |
|------|-----------|------|---------|
| 5.2 骨架生成 | knowledge-cache(~2459行) + analysis-report(~125行) + conversion-plan(~88行) ≈ **2672行** | 9个骨架文件 × ~50行 ≈ **450行** | 9次 `write_to_file` |
| 5.3 填充（×9次） | knowledge-cache(~2459行) + 骨架文件(~50行) + 源文件(~100-900行) + 样式文件(~50-250行) ≈ 每次 **2659~3659行** | 每次 `replace_in_file` 输出 ~100-350行 | 每文件: 1次 `read_file`(骨架) + 1次 `read_file`(源码) + 1~3次 `replace_in_file` |

**总输入 token**：骨架生成 1次 ~2672行 + 填充 9次 × ~3100行 ≈ **30,572行**
**总输出 token**：骨架 ~450行 + 填充 ~2000行 ≈ **2,450行**
**工具调用**：9(write) + 9(read骨架) + 9(read源码) + 9~27(replace) ≈ **36~54次**

> **隐性成本**：`replace_in_file` 需要精确匹配 `old_str`，当骨架格式与实际填充不匹配时触发失败重试，每次重试需重新 `read_file` + `replace_in_file`，额外消耗约 **+3000~5000行/次**。实际执行中骨架填充不匹配概率约 20~30%。

### 方案 B Token 流

| 阶段 | 输入上下文 | 输出 | 工具调用 |
|------|-----------|------|---------|
| 5.2 转换（×9次） | knowledge-cache(~2459行) + analysis-report(~125行) + 源文件(~100-900行) + 样式文件(~50-250行) + 已转换文件(按需~0-200行) ≈ 每次 **2734~3934行** | 每次 `write_to_file` 输出 ~100-400行 | 每文件: 1次 `read_file`(源码) + 1次 `write_to_file` |
| 5.3 整理 | knowledge-cache(~2459行) + 全部已转换文件(~2000行) ≈ **4459行** | 少量 `replace_in_file` 修正 ~200-500行 | ~5-10次 `read_file` + ~3-5次 `replace_in_file` |

**总输入 token**：转换 9次 × ~3300行 + 整理 1次 ~4459行 ≈ **34,159行**
**总输出 token**：转换 ~2000行 + 整理 ~350行 ≈ **2,350行**
**工具调用**：9(read源码) + 9(write) + 5~10(read整理) + 3~5(replace整理) ≈ **26~33次**

> 无 `replace_in_file` 匹配失败风险（转换阶段使用 `write_to_file` 直接写入）。

### Token 对比汇总

| 指标 | 方案 A | 方案 B | 差异 |
|------|--------|--------|------|
| 总输入行数（理论） | ~30,572行 | ~34,159行 | B 多 ~12% |
| 总输出行数 | ~2,450行 | ~2,350行 | 基本持平 |
| 工具调用次数 | 36~54次 | 26~33次 | **B 少 30~40%** |
| replace 失败重试（预期） | 2~3次 × ~4000行 | 0~1次 × ~3000行 | **B 少 ~8000-12000行** |
| **实际总 token（含重试）** | ~40,000-42,000行 | ~34,000-37,000行 | **B 少 ~10-15%** |

**结论**：方案 B 理论输入略多 12%，但因工具调用少 30-40% 且无骨架匹配失败风险，**实际总 token 消耗反而少 10-15%**。

## 准确性分析

### 评估维度

#### 1. 架构一致性（目录结构 / 类继承 / 代码风格）

| 方案 | 评分 | 说明 |
|------|------|------|
| A | ★★★ | 骨架先行，类定义/继承/import 在填充前已固定，**强制约束所有文件遵循同一架构** |
| B | ★★☆ | 依赖每次转换时 LLM 自行遵循示例代码规范，一致性取决于 prompt 质量和 LLM 稳定性 |

方案 A 在此维度有天然优势：骨架是一次性生成的，确保所有文件的类签名、继承关系、方法命名风格一致。方案 B 在 9 次独立转换中可能出现风格漂移。

#### 2. 业务逻辑完整性（功能覆盖 / 分支完整 / 状态管理）

| 方案 | 评分 | 说明 |
|------|------|------|
| A | ★★☆ | 填充阶段受骨架约束，**骨架可能过早固化错误的类结构**，导致填充时被迫适应错误骨架而遗漏逻辑 |
| B | ★★★ | 每个文件独立完整转换，LLM 有完整上下文理解业务逻辑，**自由度更高，不受骨架约束** |

这是方案 A 的核心弱点。骨架生成时只看了分析报告和示例代码，**没有逐行分析源文件的业务逻辑**，容易出现：
- 属性遗漏：骨架中未声明的 observable 属性，填充时需要新增
- 方法签名错误：参数类型/数量与实际业务不匹配
- 类结构不合理：该拆分的没拆、该合并的没合

#### 3. 骨架-实现匹配度

| 方案 | 评分 | 说明 |
|------|------|------|
| A | ★☆☆ | **核心痛点**：骨架基于高层分析生成，与实际业务逻辑细节存在 gap |
| B | ★★★ | 不存在此问题（无骨架） |

visitors 页面实际转换中的典型匹配问题：

```
骨架定义:  class VisitorsViewModel : BaseViewModel<VisitorsPager>() {
              val visitors = observableList<VisitorInfo>()
              fun loadVisitors() { /* TODO */ }
           }

实际需要:  class VisitorsViewModel : BaseViewModel<VisitorsPager>() {
              val visitors = observableList<VisitorInfo>()
              val pageState by observable(PAGE_INIT)    ← 骨架中遗漏
              val isHost by observable(true)             ← 骨架中遗漏
              val isLock by observable(false)            ← 骨架中遗漏
              ... (还有 10+ 个 observable 属性)
              private val requestingMap = mutableMapOf() ← 骨架中遗漏
              fun loadVisitors() { ... }
              fun initPage() { ... }                     ← 骨架中遗漏
              fun handleGetClickMap() { ... }            ← 骨架中遗漏
              ... (还有 15+ 个方法)
           }
```

填充时需要大量修改骨架本身，骨架的"约束"反而变成了"障碍"。

#### 4. 文件间依赖准确性

| 方案 | 评分 | 说明 |
|------|------|------|
| A | ★★★ | 骨架中预设了所有 import 和引用关系，填充时直接使用 |
| B | ★★☆ | 逐文件转换时后面的文件需推断前面文件的导出，可能出现 import 路径错误 |

方案 B 的劣势可通过步骤 5.3 的架构整理来弥补（全局扫描修正 import）。

#### 5. replace_in_file 操作稳定性

| 方案 | 评分 | 说明 |
|------|------|------|
| A | ★☆☆ | 填充需要精确匹配骨架中的 `// TODO` 区域作为 `old_str`，匹配失败概率高 |
| B | ★★★ | 转换阶段全部使用 `write_to_file` 直接写入，无匹配风险 |

`replace_in_file` 失败的常见原因：
- 骨架中的空行/缩进与预期不符
- 多个 `// TODO` 位置导致 `old_str` 不唯一
- 填充内容超出骨架预设的边界，需要修改骨架结构

每次失败需要重新 `read_file` 确认当前内容后重试，额外消耗 ~4000行 token。

## 适用场景

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 文件数多（>15）、业务逻辑简单 | A | 骨架约束价值大，填充工作量小，匹配失败概率低 |
| 文件数适中（<15）、业务逻辑复杂 | **B** | 业务逻辑完整性优先，骨架约束反而是障碍 |
| 文件间强耦合、import 关系复杂 | A | 骨架预设 import 减少引用错误 |
| 文件相对独立、组件化程度高 | **B** | 独立转换效率高，整理成本低 |
| 首次使用、需要快速验证效果 | **B** | 工具调用少，失败率低，调试成本低 |

## 结论

**推荐方案 B**（先逐文件完整转换，后架构整理），理由：

1. **实际 token 更少**：虽然理论输入略多 12%，但消除了骨架匹配失败的重试成本，实际总消耗少 10-15%
2. **业务逻辑更准确**：每个文件独立完整转换，LLM 专注于当前文件的业务逻辑，不受骨架约束干扰
3. **工具调用更稳定**：使用 `write_to_file` 替代 `replace_in_file` 进行骨架填充，消除匹配失败风险
4. **架构一致性可兜底**：步骤 5.3 作为事后审查，可修正转换过程中的架构偏差

方案 A 的核心问题是**骨架的信息量不足**——它基于高层分析报告生成，无法预见源文件的业务逻辑细节，导致骨架与实际需求之间存在 gap。这个 gap 在填充阶段转化为修改骨架的额外成本和业务逻辑遗漏的风险。

如果选择方案 B，需要在步骤 5.2 的 prompt 中**强化架构遵循指令**（要求每个文件转换时必须参照示例代码的架构模式），以弥补没有骨架约束带来的架构一致性风险。
